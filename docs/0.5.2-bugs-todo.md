# Bug 1: play-from-here loses eval history

## Problem

Forking a game via play-from-here discards the eval graph: the
seeded plies 0..cursor had evals in the view game, but the new play
game starts with an all-None eval history, so the chart is empty
until new moves accumulate evals.

## Mechanism

`play_from_here` seeds moves, clocks, and comments into `new_game`,
but not evals; `new_game` hard-resets `eval_history=[None]*n_plies`.

## Approach

1. `new_game` gains `seed_eval_history: list[dict | None] | None`,
   handled like `seed_comments`: truncate/pad to `n_plies`, all-None
   collapses to the plain `[None]*n_plies` default.
2. `play_from_here` passes `self._view_eval_history[:cursor]`.

No other changes: play and view share the same per-ply eval dict
shape (play -> view hands the dicts over verbatim), the play state
payload already ships `eval_history`, and persistence and PGN
export already handle it.

## Test plan

Live-test first: play with the eval graph up, click back,
play-from-here, chart keeps the prefix. Existing suite stays green.

Formal tests after live-pass (test_play_mode_fsm /
test_e2e_play_from_here):

- fork mid-game: new game's `eval_history` equals the view prefix
- view without evals: forked game seeds all-None
- persistence round-trip keeps seeded evals

# Bug 2: player name stored client-side only

## Problem

The gameplay human name lives in localStorage
(`sturddle:player_name`), so every browser/device gets its own name
(default until set). Single-user app: all clients should reflect
one name, stored server-side like the sibling play settings
(`human_side`, TC, takeback, ...).

## Mechanism

Settings dialog reads/writes localStorage; the client sends
`player_name` per-request on `/game/new` and
`/game/view/play-from-here`; the server only keeps it inside each
game bundle. `player_name` is absent from `PERSISTED_FIELDS`.

## Approach

1. Add `player_name` to `Settings` (default "Player") and to
   `PERSISTED_FIELDS`; expose via GET/PUT `/settings` like the
   other play fields (trim, cap at the existing max length).
2. Server uses its persisted name in `new_game` /
   `play_from_here`; client stops sending `player_name`.
3. Settings dialog edits the field through the settings API;
   drop the localStorage key. One-time migration: if the server
   name is unset and localStorage has one, push it, then clear.

## Test plan

Live-test first: set name in settings, new game shows it; second
browser shows the same name; server restart keeps it. Existing
suite stays green.

Formal tests after live-pass:

- settings API round-trip persists `player_name` (trim + length cap)
- `new_game` and `play_from_here` use the persisted name with no
  `player_name` in the request payload
- migration: localStorage name pushed once to an unset server name
